# Purpose

PPS-3200 is the constitutional authority governing every Platform Application. It establishes the common application contract, shared ownership model, composition rules, validation obligations, and evolution controls that every Volume 32 child inherits.

# Scope

This specification governs application identity, responsibility, composition, services, capabilities, workflows, intelligence, data, permissions, security, accessibility, lifecycle, versioning, communication, validation, and future evolution.

It does not assign role authority, invent product artifacts, define implementation technologies, or replace canonical platform capability and data authorities.

# Authority

PPS-3200 inherits PPS-000 through PPS-015, Volume 30, and PPS-3100. Child application specifications may narrow this contract but shall not weaken it. Conflicts follow PPS-015.

# Definition of a Platform Application

A Platform Application is a governed, versioned platform product that composes registered capabilities into coherent workflows and experiences for one or more authorized Role Operating Systems.

A Platform Application is not:

- Owned by one Role Operating System.
- A permission grant or role definition.
- A private copy of a shared platform capability.
- A competing canonical data store.
- A route, screen, component, API, or vendor integration in isolation.
- An implementation authorization without validated downstream specifications.

# Architectural Philosophy

Platform Applications are durable constitutional products, not route collections or deployment units. They organize coherent user outcomes above capabilities and services while remaining below Role Operating Systems in composition authority.

The governing dependency direction is:

Constitution → Platform Architecture → Platform Applications → Platform Capabilities → Platform Services → Infrastructure

Role Operating Systems compose Applications by reference. They do not reverse this dependency direction, transfer ownership, or create private application variants.

# Shared Responsibilities

Every Platform Application owns a bounded mission, public contracts, application workflow state, user-facing outcomes, validation rules, failure behavior, recovery, observability, and completion evidence. Shared identity, authorization, canonical data, search, communication, analytics, design, and infrastructure remain owned by their constitutional domains.

# Inheritance Rules

Every application shall declare `parent: PPS-3200`, inherit PPS-3295 through PPS-3299, preserve all upstream security, data, accessibility, analytics, and intelligence controls, and identify every stricter child rule explicitly. Omission does not cancel inherited authority.

A child may specialize presentation, workflow, and domain rules. It may not weaken fail-closed behavior, reassign canonical ownership, invent a dependency, or silently supersede a parent contract.

# Composition Rules

Composition shall use registered capabilities, services, components, APIs, events, notifications, and projections. Each edge requires identity, owner, version, permission, data classification, failure behavior, compatibility, observability, and lifecycle.

Application composition must remain acyclic. Configuration may narrow optional modules or presentation, but cannot fork the application identity, required outcomes, permission model, data ownership, or lifecycle.

# Application Boundaries

An application boundary contains only workflow state and artifacts necessary for its mission. A route, table, service, vendor, component, model, or deployment boundary does not independently establish constitutional ownership.

Before creating or expanding an application, governance shall prove distinct responsibility, cross-Operating-System reuse, non-duplication, resolved upstream ownership, explicit consumers, and a governed retirement path.

# Relationship to Role Operating Systems

Volume 31 governs user populations, responsibilities, relationships, and role authority. A Role Operating System composes applications by reference and supplies an authorized role context. Applications remain shared and must produce consistent constitutional outcomes across every composition.

An application shall not infer authority from being visible in an Operating System. The composing Operating System shall declare purpose, permission scope, required workflows, and data visibility.

# Relationship to Platform Capabilities

Platform capabilities are reusable technical or domain powers that applications compose. Applications shall consume registered capability contracts and shall not duplicate capability ownership to achieve presentation or role variation.

Until a future Platform Capability Architecture becomes canonical, capability references shall resolve through existing constitutional authorities and Volume 30 registries. Unresolved capability ownership blocks implementation.

# Relationship to Intelligence Engines

Intelligence engines supply explainable, evidence-grounded proposals through governed interfaces. Applications present those proposals, preserve uncertainty and provenance, collect human decisions, and dispatch accepted actions through authorized commands.

An application shall not silently promote an inference to canonical fact, expand data access for an engine, or bypass human oversight required by PPS-005, PPS-006, and PPS-1200 through PPS-1209.

# Relationship to Platform Experience Architecture

Platform Experience Architecture governs shared interaction, navigation, screen, component, responsive, and accessibility contracts. Applications compose those registered experience artifacts without redefining their ownership. An application-specific experience may narrow presentation for an authorized context but shall preserve canonical application identity and equivalent outcomes.

# Shared Application Principles

Every application shall:

- Remain a shared platform product.
- Compose registered capabilities and product artifacts.
- Preserve least privilege and purpose limitation.
- Use canonical records rather than shadow data ownership.
- Expose deterministic, auditable lifecycle transitions.
- Support accessible and responsive outcomes.
- Fail closed when identity, context, dependency, or authorization is uncertain.
- Preserve human agency for consequential decisions.

# Capability Composition

Capability composition shall be explicit, version-compatible, permission-aware, and traceable. Each child shall identify required and optional capabilities, their owners, inputs, outputs, failure behavior, and degradation rules before implementation.

Composition shall not create circular ownership. An application may orchestrate capabilities but does not become their constitutional owner.

# Data Ownership

Data remains owned by the canonical domain named in PPS-011 and applicable data architecture. Applications may consume authorized projections, hold purpose-limited workflow state, and submit validated commands. They shall not establish a competing person, record, permission, event, or evidence source of truth.

Every application shall document classification, provenance, minimization, retention, deletion, portability, sharing, audit, and migration rules before canonical maturity.

# Permissions

Applications shall enforce least privilege at presentation, service, API, and data boundaries. Permissions derive from authenticated identity, constitutional role authority, relationship context, resource ownership, consent, and explicit policy.

Client visibility is not authorization. Unknown or conflicting permission context shall fail closed and produce auditable denial evidence.

# Security

Every application shall define its trust boundaries, threat model, abuse cases, secrets handling, input validation, dependency integrity, audit requirements, incident behavior, and recovery controls. Security controls shall be testable and inherited across every Operating System composition.

# Accessibility

Applications shall provide equivalent outcomes across keyboard, assistive technology, reduced motion, high contrast, zoom, mobile, and responsive desktop contexts. Accessibility acceptance criteria, testing evidence, and exception governance are required before release.

# Shared Analytics

Applications emit registered events and consume defined metrics under PPS-3298. Analytics shall distinguish operational health, audit evidence, product behavior, and user outcomes; it shall not become canonical domain truth or covert authorization.

Every metric requires identity, owner, population, definition, source, exclusions, freshness, privacy controls, limitations, and reproducibility evidence.

# Shared Intelligence Integration

Applications may consume intelligence only through PPS-005, PPS-006, and PPS-1200 through PPS-1209 contracts. Authorized projections flow into engines; explained proposals flow back to applications; accepted actions return through validated commands.

Models and agents may not expand their own permissions, conceal uncertainty, fabricate evidence, or commit consequential state without the decision authority declared by the application.

# Lifecycle

Application specifications follow:

Draft → Review → Approved → Canonical → Deprecated → Archived

Implementation lifecycle, release lifecycle, and document lifecycle are distinct. A canonical specification does not authorize execution without validated contracts, work packages, authorization, and release evidence.

# Application Versioning

Applications use semantic specification versions. Compatible clarification increments the patch version; additive governed capability increments the minor version; breaking contract change requires a major version, migration plan, compatibility window, and constitutional review.

Identifiers remain stable across versions. A rename shall not silently create a new constitutional identity.

# Cross-Application Communication

Applications communicate through registered APIs, commands, events, and notifications. Direct access to another application's private workflow state is prohibited.

Each interaction shall declare producer, consumer, schema identity, authorization, data classification, ordering, idempotency, failure behavior, observability, version compatibility, and audit evidence. Cycles and duplicated ownership fail validation.

# Shared Navigation Principles

Global, local, and cross-application navigation shall use registered destinations, stable identities, permission-aware visibility, accessible interaction, deterministic deep linking, and independently validated destination authorization. PPS-3297 governs navigation consistency across Operating Systems, Universes, mobile, and desktop contexts.

# Shared Design Standards

Applications shall compose the canonical design language, tokens, layouts, typography, color, components, responsive rules, and accessibility standards. Role, Universe, or device variation shall use governed configuration and shall not fork shared design authority.

# Constitutional Governance

Material changes require identifier validation, dependency review, role-composition impact analysis, data and security review, accessibility review, and registry updates. Application-specific implementation shall remain blocked while required references are unresolved.

Every application shall conform to PPS-3295 through PPS-3299. Exceptions, duplicate application responsibilities, and conflicting ownership require constitutional amendment under PPS-015.

# PBOS Responsibilities

PBOS shall validate:

- Unique identifiers and assigned numbering ranges.
- Complete, parseable metadata and required headings.
- Parent inheritance from PPS-3200.
- Resolved constitutional and product dependencies.
- Shared ownership and non-duplication boundaries.
- Registered workflows, APIs, events, data objects, and capabilities.
- Explicit permissions, security, accessibility, analytics, and lifecycle rules.
- Cross-application communication and compatibility evidence.

# PBOS Build Contract

PBOS planning shall bind the application identifier and specification version to immutable repository context, constitutional dependency closure, registered product artifacts, an execution contract, work package, authorization decision, validation evidence, release state, and completion evidence.

PBOS shall generate at most one deterministic next-gate recommendation. It shall not infer missing capabilities, services, Universes, dependencies, permissions, or completion. Unknown or conflicting identity fails closed.

Implementation eligibility requires:

1. Canonical metadata and complete dependency closure.
2. Registered features, screens, workflows, navigation, components, APIs, data objects, events, notifications, intelligence, integrations, and releases.
3. Explicit security, privacy, accessibility, performance, recovery, observability, test, and documentation contracts.
4. Immutable context, authorization, validation, release, and completion artifacts.

# Validation Rules

A Platform Application is structurally valid only when its identifier, parent, dependencies, relationships, required sections, and registry entry resolve. It becomes implementation-eligible only after application-specific services, capabilities, workflows, data, permissions, interfaces, failure states, tests, and completion evidence are explicit and validated.

PBOS shall fail closed on missing metadata, unknown references, conflicting ownership, stale evidence, undocumented communication, or ambiguous authorization.

# Future Evolution

New applications require evidence that the proposed outcome cannot be fulfilled through an existing application plus governed capability composition. Extensions shall prefer compatible configuration and registered services over forks.

Deprecation requires a successor or retirement rationale, data and workflow migration, compatibility plan, stakeholder communication, and historical preservation. Future constitutional volumes may refine capability or implementation contracts but shall preserve this framework's shared ownership, authority, and fail-closed guarantees.

# Future Expansion

Future capability, service, infrastructure, Universe, screen, and implementation volumes shall reference PPS-3200 rather than duplicate its application authority. They may define lower-level contracts and registries while preserving application identifiers, ownership, composition, and governance.

Reserved PPS-32 identifiers require constitutional allocation. A new application must pass overlap analysis against every existing Volume 32 child and prove why extension of a canonical application is insufficient.

# Definition of Done

PPS-3200 is complete when the definition, authority, shared ownership, composition model, data and permission boundaries, security, accessibility, lifecycle, versioning, communication, governance, PBOS validation, and evolution rules are explicit and registered.
