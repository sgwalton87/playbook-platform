# Relationship Security Observability

## Purpose

Make support-relationship security changes measurable, participant-visible, and auditable without creating a second canonical relationship record.

## Canonical ownership

`support_relationships` remains the canonical relationship source.

`relationship_security_events` is append-only derived audit evidence. It records security-relevant transitions produced by mutations of the canonical relationship row.

## Recorded events

- `relationship.activated`
- `relationship.revoked`
- `relationship.blocked`
- `relationship.status_changed`
- `relationship.permissions_changed`

Each event preserves the relationship identity, Scholar, supporter, actor when available, previous/new status, previous/new permissions, and occurrence time.

## Access boundary

Relationship audit events are visible only to the Scholar owner or connected supporter through RLS.

Authenticated users cannot directly insert, update, or delete audit events. Events are generated by the canonical `support_relationships` trigger.

## User experience

The Support Network keeps three distinct layers:

1. the existing visual orientation map;
2. canonical live relationship management;
3. append-only relationship security history.

These layers must not be presented as interchangeable sources of truth.

## Operational metrics

The authenticated security-events API returns a bounded recent event set plus counts by event type. These are participant-scoped operational measurements, not platform-wide administrator analytics.

Future platform-operator aggregation must preserve privacy and authorization boundaries.

## Security invariants

- Relationship events never grant permissions.
- Audit history cannot be used to restore revoked access.
- Revocation remains canonical on `support_relationships`.
- Audit rows are not deleted when a relationship ends.
- Unrelated authenticated users cannot read another relationship's event history.

## Constitutional alignment

This decision implements the platform requirements for security-by-default, auditability, single-source-of-truth data ownership, and measurable major capabilities.

## External certification gates

Production certification requires:

1. governed application of the relationship migration chain;
2. RLS acceptance proving participant-only event visibility;
3. activation/revocation acceptance proving exactly one expected security event per canonical transition;
4. browser acceptance of loading, empty, populated, and error states;
5. verification that no sensitive relationship history is exposed outside authorized participants.
