## Executive Summary

The committed repository defines **47 table declarations and 465 declared columns** across 18 migrations. It defines no committed SQL view. The authoritative student graph is `playbook_records` plus its achievement, evidence, verification, reflection, outcome, evidence-pack, timeline, match, trust, and vault relations. Runtime code also queries pre-existing Supabase entities whose creating DDL is absent from this repository; their full deployed shape and policy cannot be inferred and is therefore marked **Unknown**, never assumed.

The discovery found two material traceability hazards: `trust_reports` is declared twice with incompatible meanings, while onboarding/profile code uses both top-level profile columns and `onboarding_data` aliases. These are documented gaps—not authorization to redesign the Record. No runtime model or schema was added by this sprint.

## Method, Scope, and Evidence Rules

- Scope: every Git-tracked file (`git ls-files`), with implementation evidence taken from migrations, `.from()` calls, domain types, routes, components, tests, and current handbook/audit documents.
- “Field” below means every column declared by committed SQL plus every named field in the canonical/intelligence boundary contracts. JSONB inner keys are workflow-defined and are called out rather than fabricated as database columns.
- “Existing UI/API” means a direct repository consumer or the closest owning surface. “Not evidenced” is not equivalent to nonexistent in a deployed Supabase project.
- Supabase Auth (`auth.users`) and Storage are managed external schemas. This repository references them but does not define all their fields.
- Historical/backup files were inspected for coverage but are not treated as current runtime authority.

## Legend

`Implemented` = schema and consumer evidence; `Partial` = one layer or adapter exists; `External/unknown` = queried but DDL is absent; `Conflict` = incompatible declarations or ownership; `Future` = constitutionally proposed, not implemented.

## Permissions and Ownership Findings

1. Record tables use ownership helpers and RLS in `20260701_playbook_graph.sql`; field-level permission is not available in PostgreSQL RLS, so sensitive JSON keys inherit the row policy.
2. Later feature migrations enable RLS, but policy strength varies. A source-level policy presence is not runtime proof and does not establish deployed migration state.
3. Direct browser Supabase access exists for profiles, academics, social, and connections; server APIs exist for application, event, support, reward, store, albums, and moderation workflows. Application authorization and RLS need parity testing.
4. Verification authority is explicit only where verifier/moderator/issuer/rules fields exist. Boolean `verified` without provenance is a claim, not sufficient authority.
