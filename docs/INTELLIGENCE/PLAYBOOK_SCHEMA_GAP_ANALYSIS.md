## Executive Summary

The Scholar Record already exists and remains canonical. The schema is broad enough to hold verified growth, reusable evidence, opportunity progress, support relationships, events, applications, athletics, social activity, moderation and economy state. The dominant gaps are not a lack of another student record; they are incomplete committed DDL for runtime dependencies, inconsistent adapters/provenance, a `trust_reports` name collision, loosely typed JSON payloads, and unfinished lifecycle/permission contracts.

The smallest safe next moves are recovery and clarification: commit authoritative definitions for externally existing tables, resolve only proven name/shape collisions through reviewed migrations, map onboarding aliases into existing canonical fields, add provenance/lifecycle metadata to current entities, and test policy parity. No feature implementation is included here.

## Orphan-Field Audit

“Orphan” here means a committed column with no direct `.from()` consumer or a captured UI value with no evidenced downstream read. It does not mean safe to delete.

| Finding                                                                                                                                       | Evidence                                 | Classification                          | Action                                                                         |
| --------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------- | --------------------------------------- | ------------------------------------------------------------------------------ |
| Several feature tables have no direct runtime query (`athlete_*`, `recruiting_targets`, `nil_deals`, `brand_partners`, some Record relations) | Data map direct-consumer inventory       | Partial workflow / potentially orphaned | Confirm intended repository adapter and deployed use before any deletion.      |
| `metadata` and `ai_context` JSONB recur across Record tables without committed inner schemas                                                  | Playbook graph DDL                       | Undocumented inner data risk            | Inventory actual keys from deployed data; define typed adapters and retention. |
| Onboarding GPA, graduation year, activity and athlete keys are JSON-only while consumers read top-level/normalized fields                     | onboarding audit and `/start`/`/profile` | Orphaned workflow values                | Map through existing profile/Record adapter; no new field.                     |
| Portfolio/application/recommender JSON arrays contain copied snapshots/references without schema constraints                                  | application toolkit DDL/APIs             | Partial provenance                      | Version payload shape and preserve Record/evidence IDs.                        |
| No direct code consumer does not prove a database column is unused                                                                            | source-only limitation                   | Unknown                                 | Use query telemetry/deployed schema/data audit before deprecation.             |

## Minimum Extension Sequence (Recommendation Only)

1. **Recover facts:** export/compare deployed Supabase schema, indexes and policies for every missing-DDL entity; commit a reviewed baseline without destructive recreation.
2. **Resolve proven conflict:** audit deployed `trust_reports`, then produce a data-preserving rename/migration plan with API/RLS updates.
3. **Map, do not copy:** document and test onboarding/profile/Scholar field mapping and external source IDs.
4. **Type existing boundaries:** narrow `LegacyValue` and JSON payloads through adapters; add source/version/evidence references to projections and outputs.
5. **Prove permissions:** role/relationship RLS parity tests, storage-policy review, share expiry and revocation tests.
6. **Only then extend engines:** add the smallest fields/states to opportunity, verification, support, workspace, event, or vault entities required by approved engine work.

## Validation Conclusions

- **No duplicate canonical student model:** verified. `ScholarRecord` is a projection/domain model and `playbook-record` re-exports/reuses the Scholar domain.
- **No duplicate data models at all:** not verified. One proven `trust_reports` collision, repeated social declarations, and several semantic overlaps exist.
- **No orphan fields:** not verified. Source evidence identifies unconsumed committed columns and onboarding values; deployed usage telemetry is required before calling them removable.
- **No duplicate workflows:** not verified. Connections/support and source achievement/Record mapping need semantic ownership decisions.
- **No conflicting ownership:** not verified. The `trust_reports` collision is a direct conflict; profile/onboarding mapping is ambiguous.
- **No undocumented data:** not verified. Missing DDL and unconstrained JSONB mean the repository cannot enumerate deployed data completely.
- **Repository coverage:** 100% of tracked paths inventoried; data-definition certification **84.3%**, with the scoring method in the data map.

These failures are discovery results, not test failures and not permission to redesign the Scholar Record.
